# 불편사항 정리 (Pain Points)

## 실행 요약

- 인터뷰: 1회 (페르소나당 최대 3턴)
- 다뤄지지 않은 기능: 없음

## 기능 목록

| ID | 이름 | 요약 |
| --- | --- | --- |
| F1 | 지인 풀 등록·관리 | 이름, 관계(대학·직장·가족 등), 연락처를 등록하고 한 사람을 여러 그룹에 동시에 소속시킬 수 있다. |
| F2 | 모임 편성 | 등록된 지인 중 일부를 골라 하나의 모임으로 묶는다. |

| F4 | 확정 및 공유 | 최종 날짜가 정해지면 모임 구성원 전원이 확인할 수 있다. |

| F6 | 진행 상태 구분 | 회신 대기 중, 확정 대기 중, 확정됨, 다녀옴 상태를 구분해서 본다. |

## 통과 항목 상세

### bride-1 (functional · F1, F2)
- **설명**: 한 사람이 여러 모임에 중복 소속될 수 있지만, 새 모임을 만들거나 다른 모임에 배정할 때 '이 사람이 이미 다른 모임에 들어가 있음'을 알려주는 경고/표시 기능이 없어 사용자가 여전히 기억에 의존해 수동 대조해야 함
- **인용**: "이 앱도 그냥 여러 그룹에 넣을 수 있다고만 하고 \"이번 모임에 이미 넣은 사람\"이라고 표시나 경고를 안 해주면, 결국 제가 머릿속으로 다 기억하고 있어야 하는 건 똑같은 것 같아요."
- **검증 코멘트**: 페르소나(6~7개 접점 없는 무리, 한 사람이 여러 무리에 걸침)와 정확히 부합하며, F1(다중 그룹 소속)·F2(모임 편성) 기능이 실제 존재하므로 전제를 지어낸 것이 아니다. 제품 소개서가 이 안내 방식을 미정으로 남긴 지점을 정확히 짚었으며, 인용문이 불편의 핵심(수동 대조 부담)을 직접 뒷받침한다.

### bride-2 (functional · F1, F2, F4)
- **설명**: 한 사람을 최종적으로 어느 모임에 '배정 확정'했는지 표시해주는 기능이 없어, 중복 소속된 사람의 최종 참석 모임을 판단하기 위해 여러 카톡방을 뒤져야 하고 청첩장 중복/누락 위험이 그대로 남음
- **인용**: "한 사람을 최종적으로 어느 모임에 \"배정 확정\"했는지 표시해주는 기능이 있는지는 안 나와 있어서 모르겠네요."
- **검증 코멘트**: 페르소나의 좌절 포인트와 정확히 일치하며, 소개서가 명시적으로 열어둔 지점을 짚었다. F1·F2·F4가 맞물리는 지점의 실질적 기능 공백. 다만 F2/F4 중 어느 단계 문제인지 경계가 다소 모호하다는 점은 v2 PRD 작성 시 유의.

### bride-3 (functional · F3)
- **설명**: 회신 마감 기한을 설정할 수는 있지만 마감 후 자동 처리나 판단 지원 기능이 없어 무응답자를 얼마나 더 기다릴지, 없이 확정할지를 여전히 사용자가 감으로 판단해야 함
- **인용**: "결국 저는 \"4명 답 왔고 1명 무응답, 이 사람 없이 그냥 날짜 잡을까 말까\"를 매번 판단해야 하는 스트레스는 그대로일 것 같아요."
- **검증 코멘트**: F3는 마감 기한만 명시하고 마감 이후 무응답자 판단 지원은 소개서 어디에도 없어 실제로 정의되지 않은 공백. 페르소나 좌절 포인트와도 정확히 부합.

### bride-4 (functional · F3, F4)
- **설명**: 마감 후 확정된 뒤 뒤늦게 회신이 온 사람을 앱 내에서 처리하는 방법이 있는지 불명확하여, 결국 앱 밖 카톡으로 별도 연락해야 할 것으로 예상됨
- **인용**: "이걸 앱 안에서 처리하는 방법이 있는지 없는지도 모르겠고, 아마 결국 카톡으로 따로 얘기하게 될 것 같아요."
- **검증 코멘트**: F3와 F4의 경계에서 발생하는 실제 미결정 사항. 마감 후 지각 회신 처리 플로우가 소개서에 전혀 언급되지 않아 사소한 취향이 아닌 설계 이슈.

### bride-5 (functional · F5)
- **설명**: 전체 일정 조망에서 겹침을 확정 시점에 사전 경고하거나 차단하는 기능이 있는지 소개서에 나와 있지 않아, 일정 겹침을 확정 전에 막아주는 안전장치가 보장되지 않음
- **인용**: "확정하려고 할 때 바로 그 자리에서 \"이미 겹치는 일정 있음\" 하고 막아주거나 경고해주면 정말 좋을 텐데, 그런 기능이 있는지는 소개서에 안 나와 있어서 모르겠네요."
- **검증 코멘트**: F5는 '조회 시점 확인'만 명시하며 '확정 시점 사전 경고/차단'은 언급되지 않은 실제 공백. F5의 설계(단순 조회 vs 액션형 검증)를 좌우할 실질적 질문.

### bride-6 (ux · F5)
- **설명**: 겹침을 능동적으로 알림으로 먼저 알려주는 것이 아니라 사용자가 직접 조망 화면에 들어가야 확인 가능한 방식이라면, 바빠서 확인을 놓칠 경우 지금처럼 뒤늦게 겹침을 발견하는 문제가 반복될 것으로 예상됨
- **인용**: "알림이 와서 \"이번 주 토요일에 겹쳤어요\" 하고 먼저 알려주는 게 아니면, 결국 제가 능동적으로 들어가서 봐야 아는 거잖아요."
- **검증 코멘트**: F5는 조회(pull) 화면으로만 명시되며 능동적 알림(push)은 언급이 없다. 푸시 알림 vs 풀 조회의 구조적 차이를 지적하는 실질적 이슈.

### bride-7 (ux · F6)
- **설명**: 진행 상태 구분이 탭 필터가 아니라 목록에 텍스트로만 표시되는 방식이라면, 모임이 20개 이상일 때 하나씩 읽어야 해서 지금 엑셀/카톡방을 훑는 것과 속도 차이가 크지 않을 수 있음
- **인용**: "그냥 목록에 작은 텍스트로 \"확정됨\" 이렇게만 써있으면 20개 넘는 리스트에서 눈으로 하나하나 읽어야 하니까 크게 안 빨라질 수도 있고, 탭으로 딱 나눠서... 걸러볼 수 있으면 훨씬 빠를 것 같아요."
- **검증 코멘트**: F6는 표현 방식(탭/색 등)이 정해지지 않았다고 소개서가 명시한 지점에 대한 정당한 설계 고려사항. 모임 수가 20개 이상이 될 개연성이 페르소나와 부합.

### bride-8 (ux · F5)
- **설명**: 신랑·신부 합산 조망이 단순히 달력에 점을 찍는 정도의 표시라면, 특정 주말에 모임이 몰려 있는지를 사용자가 직접 눈으로 세어야 해서 지금의 수동 확인과 큰 차이가 없을 수 있음
- **인용**: "그냥 달력에 점 찍힌 정도로만 보여주면 저는 결국 눈으로 세어봐야 해서 지금이랑 별 차이 없을 수도 있어요."
- **검증 코멘트**: F5의 레이아웃(달력형/목록형)이 미정임을 인지한 채 제기한 정당한 우려. F5의 핵심 목적(겹침을 바로 알 수 있음) 달성 여부에 직결되는 기능적 이슈. v2 PRD에서 F5 인수조건(겹치는 날짜의 시각적 구분)을 구체화하는 방향 권장.

### groom-1 (functional · F1, F2)
- **설명**: 1:1로만 만나야 하는 관계(직장 상사)를 위한 별도 개념이 없어 멤버 1명짜리 '모임'으로 우회해야 하는데, 이게 의도된 사용법인지 확신이 안 서고 '모임'이라는 표현 자체가 배우자가 볼 때 어색하고 헷갈릴 수 있음
- **인용**: "\"모임 편성\"에서 이 사람 하나만 골라서 모임을 만든다고 하면... 화면상으로 이게 \"모임\"이라는 이름으로 뜨는 게 좀 어색하긴 해요. ... 이게 의도된 사용법인지 확신이 안 서서 처음엔 좀 헤맬 것 같아요."
- **검증 코멘트**: 소개서에 1:1 관계도 모임으로 묶을 수 있다고 명시되어 있어 오독이 아니다. UI 레이블링/온보딩 명확성에 관한 실질적 이슈.

### groom-2 (functional · F1, F2)
- **설명**: 한 사람이 여러 그룹에 걸쳐 있을 때, 이미 다른 모임에도 속한 사람이라는 걸 모임 편성 시 미리 경고해주는 기능이 없어 실수로 민감한 사람(상사)을 잘못된 모임에 포함시켜 날짜 후보를 발송할 위험이 있음
- **인용**: "모임 만들 때 \"이 사람은 이미 다른 모임에도 속해 있어요\" 같은 걸 미리 알려주는 게 없으면, 저는 매번 지인 목록을 손으로 다시 확인해야 하고, 그러다 한 번은 실수로 같이 넣어버릴 것 같아 불안해요."
- **검증 코멘트**: 소개서가 스스로 미결정으로 남긴 공백을 지적. 민감한 인물을 잘못된 모임에 포함시키는 것은 실질적 기능 리스크.

### groom-3 (functional · F3, F4)
- **설명**: 이미 발송된 날짜 후보에서 멤버를 제외/취소하는 방법과, 제외 시 해당 멤버에게 취소 알림이 가는지 여부가 정의되어 있지 않아 실수 수습이 앱 밖(직접 연락)에서 이뤄질 수밖에 없음
- **인용**: "\"확정 및 공유\" 앞 단계에서 이미 나간 후보를 수정·취소하는 방법이 뭐라고 되어 있는지가 안 나와 있어서 여기서 또 막힐 것 같아요. 멤버를 뺄 수는 있는지, 빼면 상사한테 \"취소됐다\"는 알림이 또 가는 건지..."
- **검증 코멘트**: F3→F4 사이의 취소/제외 흐름이 언급 자체가 없는 실제 스펙 공백. 상사와의 1:1 관계 특수성과도 부합.

### groom-4 (functional · F3)
- **설명**: 회신하지 않은 사람만 걸러서 보거나 그들에게 콕 집어 리마인드를 보내는 기능이 없어, 결국 카톡으로 직접 물어보는 기존 방식을 그대로 재현하게 됨
- **인용**: "누가 아직 회신 안 했는지 콕 집어서 리마인드를 보낼 수 있는지는 안 나와 있어서... 지금 카톡으로 조율하는 것과 똑같은 상황이 재현되는 거죠."
- **검증 코멘트**: F3 명세에 필터링/개별 리마인드 기능이 없는 실제 공백. 이중 약속 방지·수동 조율 탈피라는 목적에 실질적 영향.

### groom-5 (functional · F4)
- **설명**: 모임 확정 시 배우자에게 별도 알림이 가는지, 아니면 화면에만 조용히 반영되는지가 정의되지 않아, 배우자가 앱을 열어보지 않으면 겹침을 뒤늦게 발견할 위험이 있음
- **인용**: "배우자가 앱을 안 열어보면 그냥 조용히 화면에만 반영되고 끝나는 건지, 아니면 알림이 따로 가는 건지가 소개서에 안 나와 있어서요."
- **검증 코멘트**: F4는 "확인할 수 있다"고만 명시되어 능동 알림 여부가 실제로 정의되지 않음. 페르소나의 기존 좌절 포인트와 직접 부합.

### groom-6 (functional · F1, F2)
- **설명**: 배우자 쪽 지인을 나의 모임 편성 화면에서 함께 추가할 수 있는 공동 편집/권한 위임 개념이 없어, 상견례처럼 양가가 함께 나가는 모임의 참석자 명단을 앱 안에서 제대로 구성할 방법이 불분명함
- **인용**: "배우자 쪽 부모님은 제 지인 풀에 없잖아요? 그럼 이 모임을 만들려면 배우자가 자기 쪽 사람을 추가하는 걸 배우자한테 넘겨야 하는 건지... 소개서엔 안 나와 있어서 모르겠어요."
- **검증 코멘트**: 신랑/신부 지인 풀이 분리 관리된다는 전제 하에서 양가 합동 모임 구성 방법이 소개서에 아예 언급조차 없는 근본적 공백.

### groom-7 (ux · F3, F5)
- **설명**: 날짜 후보를 고르는 화면 안에서 배우자 쪽 확정 일정이 바로 보이지 않고, 별도의 전체 조망 화면으로 넘어가 대조해야 해서 후보 편성과 조망 화면을 왔다갔다 해야 하는 번거로움이 있음
- **인용**: "저는 상견례 날짜 후보를 고르는 그 화면 안에서 배우자 쪽 확정 일정이 바로 안 보이고, 후보를 다 정한 다음에 조망 화면으로 따로 넘어가서 확인해야 하는 흐름일 것 같은데... 이게 맞다면 굉장히 번거로워요."
- **검증 코멘트**: 두 화면이 구조적으로 분리되어 있다는 전제는 소개서와 부합. 다만 인용문 자체가 추측("일 것 같은데")임을 인정하고 있어 실제 사용 빈도·심각도는 불확실하나, 이중예약 방지라는 핵심 목적과 직결된 설계 이슈로 판단.

### groom-8 (ux · F4, F5)
- **설명**: 확정 대기 상태인 모임 화면에서 해당 날짜의 배우자 쪽 일정이 바로 보이지 않으면, 확정 버튼을 누르기 전 창 두 개를 띄워 눈으로 대조해야 하는 번거로움이 발생함
- **인용**: "확정 버튼 누르기 전에 매번 창을 두 개 띄워놓고... 날짜를 눈으로 대조해야 하는데, 이게 귀찮으면 결국 저는... 배우자한테 카톡으로 먼저 물어보고 확답 듣고 나서야 앱에서 확정 버튼을 누를 것 같아요."
- **검증 코멘트**: F4의 확정 행위와 F5의 겹침 확인이 단절되어 있어 정작 확정 순간에 겹침 검증이 불가능한 구조적 결함. 앱의 핵심 가치 제안을 우회해 기존 대안(카톡)으로 되돌아갈 위험까지 드러냄.

### groom-9 (ux · F6)
- **설명**: 진행 상태 구분이 탭이 아니라 리스트에 색 배지로만 표시되는 경우, 모임 수가 늘어날수록 스크롤하며 색을 스캔해야 해서 바쁜 짬에 한눈에 파악하기 어려움
- **인용**: "만약 리스트 하나에 색깔 배지만 붙어 있는 형태면 스크롤하면서 색을 하나하나 눈으로 스캔해야 하니까 5분 안에 다 훑기 부담스러울 것 같아요."
- **검증 코멘트**: F6의 표현 방식이 정해지지 않은 미정 설계 공간에 대한 정당한 우려. 페르소나(바쁜 평일 짬에 한 화면 파악 선호)와 정확히 부합.

### groom-10 (ux · F5)
- **설명**: 전체 일정 조망 화면이 리스트 형태로만 제공될 경우, 결혼식 임박 시점처럼 확정 모임이 많이 쌓인 상태에서 날짜를 하나하나 뽑아 머릿속으로 달력을 그려야 해서 빈 날짜를 찾기 번거로움
- **인용**: "만약 리스트 형태로 \"확정됨\" 상태인 것들만 쭉 나열돼 있으면 저는 그 리스트에서 날짜만 하나하나 뽑아서 머릿속으로 달력을 그려야 하니까 훨씬 번거로울 것 같아요."
- **검증 코멘트**: F5 레이아웃(달력형 vs 목록형) 미정에 대한 실질적 설계 지적으로, 페르소나의 기존 좌절 포인트와 일관됨.

### invitee-3 (functional · F6)
- **설명**: 진행 상태 구분(회신 대기/확정 대기/확정됨/다녀옴)이 모임 주최자 관점 기준이라, 초대받은 사람에게 정말 필요한 '내가 아직 답 안 한 것과 그 마감일'이라는 정보를 바로 제공하지 못하며, 이 상태가 초대받은 사람에게도 보이는 화면인지조차 불명확하다
- **인용**: "저는 모임 주최자가 아니라 초대받은 사람이니까 \"이 모임이 지금 무슨 상태냐\"보다 \"내가 아직 답을 안 한 게 뭐냐, 마감이 언제까지냐\"가 더 급한데 그게 저 상태 구분에 딱 안 들어맞는 것 같아요."
- **검증 코멘트**: 게스트가 이 상태 화면을 보는지 자체가 소개서에서 침묵하고 있는 지점을 정확히 짚었다. F6의 대상 사용자와 관점을 명확히 해야 하는 실질적 설계 공백.

### invitee-4 (functional · F4)
- **설명**: 회신 방식이 정해지지 않았고 알림에 대한 언급 자체가 없어, 모임이 확정된 순간을 앱을 직접 열어보지 않으면 알 방법이 없다
- **인용**: "소개서에는 회신 방식도 \"정해지지 않음\"이고 알림에 대한 언급 자체가 아예 없어서, 확정 사실을 어떻게 통보받는지가 제일 궁금하고 걱정되는 지점이에요."
- **검증 코멘트**: F4는 '확인 가능'만 보장하고 '통보'는 보장하지 않는 갭을 정확히 짚음. 다중 스레드에서 상태를 놓치는 페르소나 핵심 좌절과 직접 연결. (근거 문장과 featureId 매핑이 다소 헐겁다는 점은 참고사항.)

### invitee-5 (functional · F3)
- **설명**: 이미 한 회신(가능/불가능)을 취소하거나 정정하는 기능이 없어, 겹치는 날짜를 뒤늦게 발견했을 때 앱 안에서 처리할 방법이 없다
- **인용**: "이 앱은 한번 회신하면 그걸 취소하거나 바꾸는 화면이 있는지 소개서에 안 나와 있어서, 결국 저는 회신 정정하려고 또 카톡방으로 가서 신랑신부한테 따로 말해야 할 것 같아요."
- **검증 코멘트**: 회신 수정 가능 여부는 소개서 어디에도 없는 실제 공백. 여러 커플로부터 겹치는 요청을 받는 페르소나 상황과 정확히 부합.

### invitee-7 (functional · F3)
- **설명**: 앱이 개인 일정(캘린더)을 인식하거나 후보 목록에 개인 일정과의 겹침을 표시해주는 기능이 없어, 회신 여부를 판단할 때 여전히 별도 캘린더 앱과 수동 대조가 필요하다
- **인용**: "소개서에는 개인 일정을 이 앱이 따로 인식하거나 표시해준다는 내용이 없어서, 결국 목록에서 마감 임박한 걸 봐도... 캘린더 앱을 또 켜서 하나하나 대조하는 건 똑같이 해야 할 것 같아요."
- **검증 코멘트**: 페르소나의 명시적 좌절 포인트(개인 일정 수동 대조)와 정확히 부합하며, 개인 캘린더 인식/겹침 표시 기능이 실제로 없는 공백. 회신 채널이 무엇이든 본질을 무효화하지 않음.

## 탈락 항목

### invitee-1 (functional · F3, F5)
- **설명**: 여러 모임에서 동시에 들어온 날짜 후보를 날짜 기준으로 교차 조회하는 기능이 없어, 특정 날짜에 몇 개의 요청이 들어와 있고 그중 무엇을 골라야 하는지 한 화면에서 볼 수 없다
- **인용**: "제가 진짜 원하는 건 \"10/18에 나한테 들어온 요청이 몇 개고 그중 뭘 골라야 하나\"를 한 화면에서 보는 건데, 소개서에는 그런 기능은 안 보이더라고요."
- **탈락 사유**: 이 제품의 사용자는 예비신랑·예비신부이며 지인은 등록·관리 대상일 뿐 앱 사용 주체가 아니다. F5도 한 커플 내부의 신랑측+신부측 통합 조망이지, 여러 커플에 걸친 지인 개인의 교차 조회 기능이 아니다. 제품의 사용자 범위를 오독한 것으로 판단.

### invitee-2 (functional · F5)
- **설명**: 전체 일정 조망 기능은 이미 확정된 모임끼리의 겹침만 보여줄 뿐, 아직 회신 대기 중인 후보 날짜들 사이의 겹침은 보여주지 못한다
- **인용**: "조망 화면도 \"확정된\" 모임들끼리 겹치는지 보여주는 거지, 아직 회신 대기 중인 후보 날짜들끼리 겹치는지 보여주는 건 아닌 것 같아서요."
- **탈락 사유**: F5는 커플 당사자가 쓰는 화면이지 초대받은 지인이 쓰는 화면이 아니다. 최민경 자신이 그 조망 화면의 사용자라는 전제 자체가 소개서에 없는 기능을 전제로 한 오독.

### invitee-6 (functional · F5)
- **설명**: 초대받은 사람이 자신이 초대받은 여러 모임들끼리 겹치는지 확인할 수 있는 화면이 있는지 자체가 불명확하다
- **인용**: "저 같은 초대받은 사람도 \"내가 초대받은 모임들끼리 겹치는지\"를 보는 화면이 따로 있는 건지 없는 건지부터가 불명확해요."
- **탈락 사유**: F5는 한 커플 단위로 스코프가 닫힌 기능이다. 여러 커플을 아우르는 초대받은 사람 전용 조망 화면은 소개서 어디에도 언급된 적 없는, 제품 범위 밖의 기능을 전제로 한 것.

### invitee-8 (functional · F3, F4, F5)
- **설명**: 날짜 후보 제안 단계, 회신 단계, 확정 단계 중 어디에도 다른 확정 일정과의 겹침을 자동으로 체크해 경고하는 기능이 없어, 겹치는 확정을 막을 방법이 전혀 없는 구조다
- **인용**: "지금 소개서대로면 이 세 시점 어디에도 그런 대조가 없어서, 저는 결국 매번 사람이 기억하고 손으로 확인하는 수밖에 없는 구조예요."

### invitee-9 (ux · F3)
- **설명**: 회신 정정을 위한 앱 내 '문의' 기능이 있어도, 신랑신부가 즉시 확인한다는 확신이 없어 결국 익숙하고 확실한 카카오톡으로 따로 연락하게 되어 앱과 카톡을 이원화해서 쓰게 된다

- **탈락 사유**: '앱 내 문의' 기능이 있다는 것을 전제로 하지만 소개서 어디에도 그런 기능이 없다(회신 방식 자체가 미정으로만 명시됨). 소개서에 없는 가상 기능을 전제로 한 지적.
